## Review Focus

1. **ApplyPatch 解析的失败闭合**：无法解析出任何路径的 patch 必须拒绝（`INVALID_PATH_OR_CALL`），不得默认放行；patch 中**每一个**路径（含删除源与重命名目标）都必须过写范围+保护检查。
2. **按参数区分 effect 的默认方向**：未知/缺失参数取值一律按 `write`（fail-closed）；`read` 名单显式列举。
3. **schema 向后兼容**：不含新字段的旧策略与既有全部测试行为不变。
4. **纵向流程证据的真实性**：Task 5 只记录真实发生的阶段与命令输出；宿主=ZCode（本会话），guard 层宿主验证仍单列未完成。
5. **就绪脚本不得静默跳过**：`verify-dsh-guard.mjs` 在密钥缺失时显式退出并说明，不得假装通过。

**Files:**

- Test: `test/policy.test.mjs`

**Interfaces:**
- Consumes: 现有 `compilePolicy`/`evaluate`/`targetPath` 结构。
- Produces（可选新增绑定字段，均可缺省，缺省=现行为）：
  1. `bindings[host][tool]` 可含 `parser: 'unified-diff'`（与 `pathKey` 指向 patch 文本字段，如 `patch_text`；effect 必须为 `write`）。evaluate 时从文本提取**全部**涉及路径（`+++ b/x`、`+++ x`、`--- a/x` 变更/删除源与目标），逐一走 `targetPath`+写根+保护检查；一个不过即拒；提取数为 0 → `INVALID_PATH_OR_CALL`。非法头（`/dev/null` 跳过）。
  2. `bindings[host][tool]` 可含 `effectKey: '<input参数名>'` 与 `readWhen: ['view', ...]`（显式名单）：命中名单→read，否则（含缺失/未知）→write。与 `effect` 字段互斥（同时出现抛 `INVALID_TOOL_BINDING`）；`effectKey` 对应参数缺失时按 write。
  3. 编译期校验：`parser` 值合法、`effectKey`/`readWhen` 形状合法（字符串数组、非空）；未知字段名仍拒绝。
- 测试：ApplyPatch 三文件 patch（一越界→整单拒；全在范围→abstain；空/垃圾 patch→拒；`/dev/null` 新建源跳过）；str_replace_editor `command=view`→read 命中读根、`command=create`→write、未知 command→write、缺 command→write；旧式纯 effect 绑定行为与既有测试完全一致；`effect`+`effectKey` 同现→编译拒。
